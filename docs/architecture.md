## Goals

1. **Portable.** A skill works on every surface that supports Agent Skills (Claude Code, claude.ai, the Claude API) without edits.
2. **Independently versioned.** Each skill has its own version and history. A change to one skill never forces a release of another.
3. **Organized by financial domain.** Users can find and install the skills for the work they do.
4. **Auditable.** The instructions behind a piece of financial analysis are reviewable and reproducible. Every change is versioned, logged and traceable to a release.
5. **Automated.** Structure, versioning, catalogs and releases are checked and produced by tooling, not by memory.

## Concepts

| Concept | What it is | Where it lives |
|---|---|---|
| **Skill** | One folder with a `SKILL.md` (YAML frontmatter plus instructions) and optional resources. The unit Claude loads, and the unit that is versioned and released. | `skills/<domain>/<skill>/` |
| **Domain** | A financial area that groups related skills, such as `equity-research` | `skills/<domain>/`, with a `README.md` defining its scope |
| **Plugin** | A Claude Code installable bundle. Here, one plugin per domain, holding that domain's skills. | An entry in `.claude-plugin/marketplace.json` |
| **Marketplace** | The catalog of plugins that Claude Code reads from this repository | `.claude-plugin/marketplace.json` |
| **Release** | A tagged, immutable package of one skill version | Git tag `<skill>-v<version>` and a GitHub release with `<skill>-<version>.zip` |

```text
│   ├── workflows/release.yml   Tags and publishes new skill versions from main
│   ├── dependabot.yml          Keeps pinned actions and Python tools current
│   ├── CODEOWNERS              Default reviewers
│   ├── ISSUE_TEMPLATE/         Skill problem and skill proposal forms
│   └── pull_request_template.md
├── docs/                       This documentation
├── skills/
│   ├── README.md               Catalog (generated table) and domain list
│   └── equity-research/        Domain
│       ├── README.md           Domain scope; first paragraph becomes the plugin description
│       └── equity-valuation/   Skill
├── templates/                  Scaffolds for `make new` (skill and domain)
├── scripts/skillkit.py         Repository tooling (validate, catalog, versions, package, release)
├── tests/test_skillkit.py      Tests for the tooling
├── CHANGELOG.md                Repository-level changes (structure, tooling, docs)
├── CONTRIBUTING.md, SECURITY.md, LICENSE
├── Makefile                    Shortcuts for the common tasks
├── pyproject.toml              pytest and ruff settings
└── requirements-dev.txt        Pinned tool dependencies
```

`skillkit validate` enforces these layout rules:

- A `SKILL.md` lives at exactly `skills/<domain>/<skill>/SKILL.md`. Nothing is nested deeper.
- Domain and skill directory names are lowercase letters, digits and single hyphens.
- A skill's `name` equals its directory name, and is unique across all domains.
- Every domain has a `README.md`. Every skill has a `README.md` and a `CHANGELOG.md`.

## Inside a skill: progressive disclosure

Claude loads a skill in three stages, so a large body of expertise costs little context until it is needed:

| Stage | What is loaded | When | Budget |
|---|---|---|---|
| 1. Discovery | `name` and `description` from the frontmatter | Always, for every installed skill | Description at most 1,024 characters |
| 2. Instructions | The body of `SKILL.md` | When a request matches the description | Under 500 lines |
| 3. Resources | Files in `references/`, `scripts/`, `assets/` | When the instructions send Claude to them | Unbounded; long files start with a contents list |

`equity-valuation` shows the pattern. Its source standard is a single 800-line document. SKILL.md keeps the role, the four tasks, the prime directives, the workflow and the stop protocol: the rules that apply to every engagement. Each module, the data-source contracts and the reporting standard move to their own reference files. Section numbers stay the same, so cross-references like "A.9" or "T-13" resolve in every file. A section map in SKILL.md tells Claude which file holds which section, and when to read it in full.

Rules for references:

- **One level deep.** Every reference file is linked from SKILL.md. Reference files do not send Claude on to further files.
- **Long files have contents lists.** Any reference file over 100 lines starts with one, so Claude sees its whole scope even from a partial read.
- **Scripts are for deterministic work.** Calculations that must be exact belong in tested code in `scripts/`, not in prose for Claude to re-derive.

## Agent-facing and human-facing files

| File | Audience | Shipped in the release zip? |
|---|---|---|
| `SKILL.md`, `references/`, `scripts/`, `assets/` | Claude | Yes |
| `README.md` (user guide) | People choosing, installing and using the skill | No |
| `CHANGELOG.md` | People tracking changes | No |

The release zip is what claude.ai and the API receive, so it carries only what Claude needs. A Claude Code plugin install copies the whole folder. The human files sit beside the skill there, but Claude never reads them unless asked, because SKILL.md does not reference them.

## Distribution

### Claude Code marketplace

`.claude-plugin/marketplace.json` declares one plugin per domain:

```json
{
  "name": "equity-research",
  "source": "./",
  "strict": false,
  "skills": ["./skills/equity-research/equity-valuation"]
}
```

- `source: "./"` with `strict: false` makes the marketplace entry the plugin's whole manifest, with no separate `plugin.json`. The `skills` array names exactly which skill folders the plugin contains. This is the pattern Anthropic's own skills marketplace uses.
- `skillkit catalog` regenerates each `skills` array from the directory tree. A new skill joins its domain's plugin automatically, and a new domain gets a new plugin entry, described by the first paragraph of the domain's README.
- Plugin entries carry no `version`. Without one, Claude Code identifies a plugin version by the git commit. Users therefore receive every merged change when they update. Skill versions are tracked in each SKILL.md. See [versioning-and-releases.md](versioning-and-releases.md#plugin-versions).

### Release packages

Each skill version is also published as a zip, for upload to claude.ai or the API. The zip is deterministic: fixed timestamps, sorted entries, one top-level folder named after the skill. Rebuilding a version gives a byte-identical file, so its SHA-256 checksum can be verified independently.

## Automation

```text
 author ──► pull request ──► CI ─────────────────────────────► merge to main ──► release workflow
            (template)       • skillkit validate                                 • skillkit release
                             • version gate (bump + changelog)                     - tag <skill>-v<version>
                             • pytest, ruff                                        - zip + .sha256
                             • markdownlint                                        - notes from CHANGELOG
                             • claude plugin validate --strict
                             • package (artifact)
```

The same checks run locally through `make check` and the pre-commit hooks. [tooling.md](tooling.md) describes each check.

## Design decisions

**Skills are grouped by domain, not under `plugins/<domain>/skills/`.** The canonical Claude Code plugin layout would tie the repository's shape to one product. Keeping `skills/<domain>/<skill>/` makes the skill folder the portable unit, and treats the plugin as one way of distributing it. Claude Code-specific components (agents, commands, hooks) can still be added to a domain's plugin entry later.

**One plugin per domain, not one for everything.** Every installed skill's description competes for Claude's attention when choosing what to load. Installing only the domains you work in keeps triggering precise. It also gives each domain a natural owner.

**Only the portable frontmatter keys.** claude.ai and the Skills API reject any frontmatter key outside `name`, `description`, `license`, `compatibility`, `metadata` and `allowed-tools`. Claude Code-only keys would make a skill un-uploadable, so the validator forbids them. Skill-specific data goes under `metadata`, as strings: `version`, `domain` and optionally `summary`.

**Version in `metadata.version`, not in the directory name or a separate file.** The version travels inside the skill on every surface, so a loaded skill can report which version it is.

**Changelogs are written by people, not generated from commits.** For a skill, what matters is how its behavior changes, for example "the default beta method is now bottom-up". Commit messages rarely say that. Each version's changelog section becomes its release notes.

**Releases come from version bumps on `main`.** No release branch or manual tagging is needed. If a version is in SKILL.md on `main` and has no tag, it is released. CI's version gate guarantees that every change to a skill's shipped files carries a new version.
